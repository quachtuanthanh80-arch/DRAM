# Architectural Simulation & Benchmark Suite for Q-Shield

This directory provides the simulation infrastructure, trace generation utilities, and 87 cycle-accurate memory access traces used to benchmark the **Q-Shield** memory controller on **Ramulator 2.0**.

---

## 📌 1. Overview: Traces & Benchmark Workloads

Memory traces represent cycle-accurate sequences of memory commands (`READ`, `WRITE`) with timestamps, physical addresses, and access attributes. In this study, traces are categorized into 5 distinct classes:

1. **Benign Standard Workloads (`trace_benign*.trace`)**:
   - **Source**: Extracted from **SPEC CPU2017** (`mcf`, `lbm`, `omnetpp`, `gcc`) and **PARSEC 3.0** (`streamcluster`, `canneal`) benchmark suites executing on gem5.
   - **Purpose**: Measure baseline throughput, read latency, queue scheduling efficiency, and verify that the controller induces negligible overhead under normal software execution.
2. **Standard RowHammer Adversarial Workloads (`trace_rowhammer*.trace`)**:
   - **Source**: Synthetic memory attack kernels executing alternating double-sided RowHammer ($Row_{k-1}, Row_{k+1}$) at wire speed.
   - **Purpose**: Test the $O(1)$ dual-hash filter's ability to count activations, trigger rate pacing, and verify zero bit-flip leakage.
3. **Prolonged-Activation RowPress Workloads (`trace_rowpress.trace`)**:
   - **Source**: Generated by `sim/traces/generate_rowpress_traces.py` modeling prolonged open-row wordline holding times ($t_{\text{ACT}} \ge 4 \times t_{\text{RAS}}$).
   - **Purpose**: Evaluate the controller's $t_{\text{RAS\_max}}$ clamping FSM and the Adaptive Threshold Engine's capacity to detect duration-weighted leakage attacks.
4. **Multi-Sided Frequency-Domain Attacks (`trace_blacksmith.trace`)**:
   - **Source**: Generated by `sim/traces/generate_blacksmith_traces.py` implementing the Blacksmith (IEEE S&P'22) non-uniform frequency pattern across multiple aggressor rows.
   - **Purpose**: Test resilience against evasion attacks designed to bypass conventional single-row thresholds.
5. **Mixed Multi-Tenant Workloads (`trace_mixed*.trace`, `trace_multitenant_adversarial.trace`)**:
   - **Source**: Interleaved traces combining benign application threads with concurrent attacking threads sharing bank groups and memory channels.
   - **Purpose**: Quantify victim process throughput slowdown, Head-of-Line blocking mitigation, and Bank Group timing-slack bypassing.

## 🚀 3. How to Run Simulations

### 1. Prerequisites & Environment Setup
- **Python**: $\ge 3.10$ with packages from `requirements.txt` (`numpy`, `pandas`, `tabulate`).
- **Ramulator 2.0**: Cycle-accurate simulator compiled with DDR5 dual-subchannel extensions.
- **Environment Variable**: Set `RAMULATOR2_PATH` if Ramulator2 is installed in a custom directory:
  ```bash
  export RAMULATOR2_PATH=/path/to/ramulator2
  ```

### 2. Execution Commands

#### A. Attack Emulation & Defense Verification
```bash
python sim/run_attack_emulation.py
```
- **Execution Time**: $\approx 4.2$ seconds.
- **Memory Consumption**: $< 85\,\text{MB}$.
- **Output Artifacts**: `sim/results/attack_emulation_summary.json`, `sim/results/attack_emulation_report.md`.

#### B. SOTA Architecture Taxonomy & Matrix Generation
```bash
python sim/generate_sota_comparison.py
```
- **Execution Time**: $\approx 1.8$ seconds.
- **Output Artifacts**: 
  - `sim/results/apples_to_apples_cycle_accurate.json` & `.tex`
  - `sim/results/literature_reported_values.json` & `.tex`
  - `sim/results/qualitative_taxonomy.json` & `.tex`

#### C. Full Cycle-Accurate Ramulator2 Benchmark Matrix
```bash
python sim/run_benchmarks.py --config DDR5-4800 --repeat 10 --seed 12345 --verbose
```
- **CLI Options**:
  - `--config {DDR4-3200,DDR5-4800,DDR5-5600,all}`: Select target memory profile.
  - `--repeat <N>`: Set number of Monte Carlo runs (default: 1).
  - `--seed <N>`: Set random seed for statistical repeatability (default: 12345).
  - `--output-dir <path>`: Destination directory for result artifacts (default: `sim/results`).
  - `--list-configs`: Print available DRAM and workload presets and exit.
- **Execution Time**: $\approx 45 - 90$ seconds per full sweep.
- **Memory Consumption**: $\approx 350\,\text{MB}$.
- **Output Artifacts**: `sim/results/bench_meta.json`, `sim/results/bench_summary.json`, `sim/results/bench_metrics.csv`, `sim/results/benchmark_summary_table.tex`.

## 🔬 4. Benchmark Methodology & Statistical Rigor

1. **Simulation Phase Parameters**:
   - **Warmup Interval**: $100,000$ memory cycles prior to statistic logging.
   - **Execution Window**: $2,000,000$ cycles per trace.
2. **Statistical Aggregation**:
   - For stochastic runs, experiments are repeated across **10 independent iterations** (`seed = 12345` through `12354`).
   - Metrics report **Mean**, **Median**, **Standard Deviation ($\sigma$)**, and **95% Confidence Intervals (CI)**.
3. **Core Performance Metric Definitions**:
   - **Effective Throughput ($\text{MB/s}$)**: Total bytes serviced divided by execution duration:
     $$\text{BW} = \frac{\text{Total Bytes Transferred}}{\text{Simulation Cycles} \times t_{\mathrm{CK}}}$$
   - **Average Read Latency ($\text{ns}$)**: Elapsed time from AXI read address handshake (`ARVALID` $\land$ `ARREADY`) to final beat data return (`RVALID` $\land$ `RREADY` $\land$ `RLAST`).
   - **Victim Slowdown**:
     $$\text{Slowdown} = \frac{\text{Latency}_{\text{under attack}}}{\text{Latency}_{\text{isolated}}}$$
   - **False Positive Rate (FPR)**: Percentage of benign requests throttled when no attack is present:
     $$\text{FPR} = \frac{\text{Benign Requests Throttled}}{\text{Total Benign Requests}} \times 100\%$$

## ⚖️ 5. Comparison Methodology: Ensuring Fair Evaluation

To avoid misleading scientific conclusions, comparative data is strictly partitioned into three distinct tiers:

### 1. Apples-to-Apples (Directly Comparable)
- **Criteria**: Evaluated on the **exact same simulator** (Ramulator 2.0), using identical memory organization presets, clock ratios, and the exact same input trace files.
- **Included Schemes**: Baseline (FR-FCFS), BlockHammer (HPCA'21), and Q-Shield (Ours).

### 2. Literature-Reported (Contextual Comparison)
- **Criteria**: Metrics extracted directly from published manuscripts (e.g., Graphene MICRO'20, AQUA MICRO'22, Rubix ASPLOS'24, PRAC ISCA'24, DREAM ISCA'25, QPRAC HPCA'25).
- **Fairness Caveat**: These values **cannot be compared directly** as direct numerical equivalents because original papers used disparate baseline simulators (e.g., USIMM vs gem5 vs Ramulator1), different memory bus topologies, and varying attack thresholds.

### 3. Qualitative Taxonomy
- Focuses on structural architectural properties (e.g., in-DRAM silicon modifications required vs pure memory controller, rate-limiting mechanism type, error-correction capability).

## ⚠️ 6. Known Limitations of the Trace Suite

Users and reviewers should note the following experimental constraints:
1. **Trace Length & Cold-Start Effects**: Cycle-accurate traces span $2\times 10^6$ cycles. While sufficient to capture tens of thousands of RowHammer activations and epoch resets, they do not capture minute-scale long-term OS paging interactions.
2. **Synthetic Attack Regularity**: Synthetic adversarial traces represent algorithmic attack models (e.g., deterministic alternating hammer). Real-world malware running under modern preemptive operating systems may exhibit irregular execution interrupted by context switches and cache pollution.
3. **Subset of Multi-Tenant Workloads**: The multi-tenant trace suite pairs specific combinations of compute-intensive (`lbm`), pointer-chasing (`mcf`), and cloud workloads (`YCSB`). While representative, they do not exhaustively cover all commercial cloud container workloads.
